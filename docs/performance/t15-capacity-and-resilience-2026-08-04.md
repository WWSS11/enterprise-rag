# T15 容量与故障恢复验证报告

日期：2026-08-04
范围：本地隔离测试环境中的应用代码、API、双 Celery Worker、PostgreSQL、Redis、Milvus 与真实模型链路。
结论：T15 约定范围通过；结果用于给出当前版本的应用侧安全上限，不代表生产容量认证，也不包含部署方案变更。

## 测试数据与边界

- 测试前活跃数据：3 个知识库、20 份文档、10 条成员关系、13 个会话、2 个评测集、100 条审计记录。
- 控制面读取：每个接口 50 次请求，并发 10，共 300 次鉴权请求。
- 健康探针：存活与就绪接口各 500 次请求，并发 50。
- 写入链路：6 份唯一虚构 Markdown 文档并发上传，随后并发重新入库和异步删除；Worker 并发数为 2。
- 问答链路：公开、非敏感法规知识库上的 3 路并发真实流式回答。
- 本报告没有把真实内部业务资料发送给模型；临时测试知识库和会话均已归档，临时文档及向量已删除。

## 故障注入与恢复

依赖检查增加 5 秒硬超时。测试按单一依赖停止、确认失败、恢复依赖、确认就绪的顺序进行，没有同时破坏多个依赖，也没有删除数据卷或修改配置。

| 故障 | 失败表现 | 失败检测 | 恢复后结果 | 恢复确认 |
| --- | --- | ---: | --- | ---: |
| Redis 暂停 | 就绪接口 503，状态 `degraded`；限流默认 fail-closed | 33.924 ms | 就绪接口 200 | 6.265 ms |
| Milvus 暂停 | 就绪接口 503，状态 `degraded` | 19.942 ms | 就绪接口 200 | 7.001 ms |
| PostgreSQL 暂停 | 就绪接口 503，状态 `degraded` | 6.482 ms | 就绪接口 200 | 32.897 ms |
| 模型 API 异常 | 非流式接口返回清理后的 503；流式错误事件不泄露供应商细节 | 自动测试 | 应用可继续处理后续请求 | 自动测试通过 |
| Worker 任务异常 | late acknowledgement、失败拒绝和可观察重试策略保持启用 | 自动测试 | 可由队列重新投递，幂等与补偿逻辑收敛 | 自动测试通过 |

## 资源和容量建议

测试完成后的静态快照如下；它们不是峰值监控数据：API 子进程约 277 MiB RSS，Celery 主进程约 241 MiB RSS，两个 Worker 子进程各约 193 MiB RSS，前端开发服务约 101 MiB RSS；PostgreSQL、Redis、Milvus 容器内存分别约 54.84 MiB、13.64 MiB、353.7 MiB。

当前版本建议采用以下应用侧边界：

- 单页查询不超过 100 条；常用列表优先通过 `q` 缩小范围。若单租户知识库、成员或评测集超过 1000 条，应在 E06 中增加总数游标或专用搜索索引后重新验证。
- 单 API 进程以 3 路并发真实流式回答作为本轮已验证上限。继续提高前必须单独观察模型配额、首 Token P95 和 429/503 比例。
- 双 Worker 已验证可承接 6 个同时活跃的入库、重建或删除任务；在没有持续队列指标前，不建议把一次人工批次扩大到 20 份以上。
- 继续保持用户每分钟 30 次、租户每分钟 300 次的聊天限流默认值，并保持 Redis 异常时默认拒绝请求；仅在明确业务决策后启用 fail-open。
- 上传保持 50 MiB 上限、2000 个压缩条目上限和压缩展开/压缩比检查。更大的单文档应拆分后再入库。
- 长会话只取有限历史轮次，生成上下文继续受 Token 预算、TopK 和最多引用数量约束，避免上下文随会话线性增长。

## 验收结论与限制

本轮控制面、批量异步链路、并发真实问答、故障检测、恢复和队列收敛均通过，错误率为 0；服务端列表已从无界结果改为有上限的分页和搜索。T15 在当前隔离测试规模内完成。

仍需在真实首批内部业务规模可用后复测 1000 条以上列表、长时间稳态流量和资源峰值；这属于容量再校准，不否定本轮代码级故障恢复结论。由于用户要求不处理部署，本报告不提出或修改任何部署、扩缩容和基础设施配置。
